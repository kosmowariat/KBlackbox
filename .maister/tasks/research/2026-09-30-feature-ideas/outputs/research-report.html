TL;DR

  • The engine offers far more than the app exposes (about 25 engine entry points used). Ten strong features are UI-only, no Bcore change.
  • Top externally validated feature: biometric space/app lock (4 of 7 competitor families). It must also gate ShortcutActivity, which is exported and unvalidated today.
  • First batch (UI-only, low risk, testable on the single Realme RMX3363 / Android 13): housekeeping + Polish locale, hardened launcher shortcuts, permissions/health screen with restart button, running-apps indicator, then the lock.
  • Do not plan from Docs.md (APIs mostly fictional). Avoid notification listener, accessibility, Xposed, host VPN, log upload.
  • Play is largely moot for now: targetSdk 28 blocks the current target-API rule, and two shipped toggles (disable FLAG_SECURE, hide root) are high-risk on Play.

Key Decisions

  • UI-only first; Bcore only when a shipped UI feature needs it.
  • Harden ShortcutActivity before shipping the lock (shortcuts otherwise bypass it).
  • Default to sideload/GitHub distribution; Play is a later, separate decision.
  • Backup via SAF only, never All Files Access or Auto Backup.

Open Questions / Risks

  • warningNothing run on a device; one phone (Android 13).
  • warningLock is a UI gate, not encryption; other launch paths unverified.
  • warningisRunningApplication uses reflection on mTasks; service-only apps may be misreported.
  • infoPlay target-API facts come from a summarised fetch; competitor evidence is snippet-level.
  • infoBrief says icon variants exist; manifest has no activity-alias.

6. Risk view

Sideload / GitHub build OK; Play needs care or exclusion

  • exclude on PlayDisable FLAG_SECURE (high: policy forbids workarounds)
  • exclude on PlayHide root / anti-detection (high, medium confidence)
  • riskyDevice/ID spoofing profiles; APK "Open with", URL/XAPK install; disguise icon; All Files Access
  • riskyImport from installed apps: use targeted <queries>, not QUERY_ALL_PACKAGES
  • declarationAny VpnService use needs disclosure (host VPN removed anyway)

Fine on both

  • Biometric lock, shortcuts, locale, health screen, running manager, freeze, diagnostics, app grid (low)
  • Fake location (medium; page not fetched)
  • Backup via SAF (medium, low if no All Files Access)

Core container itself: medium on Play (no REQUIRE_SECURE_ENV apps; no installs without consent). targetSdk 28 is the first blocker.

Ideas to avoid

  • Notification listener (read-only, special access, high policy sensitivity)
  • Accessibility service features (high risk)
  • Xposed/LSPosed and host VPN reintroduction (removed by decision, runtime.md:6-10)
  • Crash/log upload or telemetry (diagnostics stay local)
  • Telegram, cloud sync/accounts, ads, paywalls
  • Auto Backup of the virtual data dir
  • Cell-tower spoof until setNeighboringCell bug is checked
  • Cross-space account copying (credentials)
  • Guest home-screen widgets (IAppWidgetManagerProxy, L, high)
  • Planning from Docs.md APIs; marketing the lock as encryption

7. Housekeeping and stale claims

  • Docs.md: fictional APIs (clearAppData, getInstalledApps, setAppPermission, optimizeMemory, startVirtualProcess, WebViewProxy, ...); "BlackBox forums".
  • README.md: Android 5-14 / x86 / ARMv7, JDK 17, your-repo/NewBlackbox URL, "No Root" vs "Root recommended", upstream title and credits.
  • Roadmap/vision still list Xposed and VPN toggle; RELEASE_NOTES lacks a Removed note and a 2026-09-30 entry; tech-stack says CI runs no tests or lint while the roadmap says it does.
  • Dead Xposed-era resources: 5 orphan layouts, XpModuleInfo.kt, about 14 unused strings.
  • "BlackBox" left in add_shortcut_fail_msg (en :39, zh-CN :38); typos "Launched Failed" etc.; "Fake Location(Preview)".
  • Launcher icon variants are assets only, not wired via activity-alias.
  • ShortcutActivity exported without validation (AndroidManifest.xml:59-62).
  • Dead code: requestInstallPackage always false; storage broadcast without receiver; unused finishWithResult, ListActivity.start; STORAGE_POSTPONED_KEY never reset.
  • Release readiness: debug-signed release, cleartext allowed host-wide, inline osmdroid dependency, main_git link while repo not public.
  • Possible bugs: permission re-request loop in FollowMyLocationOverlay.kt:106-122; Hangzhou default centre; setNeighboringCell writes allCell.
  • Accessibility: only 6 contentDescriptions; no non-drag reorder.

9. Conclusions and recommendations

Direct answer: add, in order, biometric lock, hardened launcher shortcuts, Polish/per-app language, permissions/health screen, running-apps manager, fake-location upgrade, backup/export, app grid upgrades, local diagnostics, freeze/auto-stop. Bcore work only for notification mute, per-app hideRoot/FLAG_SECURE, permission deny-list and spoof profiles, after the UI batch.

Methodology, gaps and sources

Mixed gap analysis: six gatherers (two codebase, one docs, three external) produced findings; synthesis cross-referenced code vs docs and competitor vs platform vs policy, then ranked by value/effort with UI-only first.

Gaps: nothing executed on device; Android 13 only; competitor sources are snippets; mock-location, notification-access and overlay policy not fetched; guest-side effects of host features untested; Android 16 hook impact unknown; launcher icon monochrome layer unverified by the app finding (platform finding says none).
