TL;DR

Theme.BlackBox is re-parented to Theme.Material3.DayNight.NoActionBar. It gets a full M3 tonal scheme from seed #3F6FD8, stored as md_theme_* in values/ and values-night/, plus dynamic color on API 31+ (main process, host activities only). Hard-coded light colors move to theme attributes. The toolbar becomes an M3 surface toolbar, forceDarkAllowed=false is removed, and the splash follows the theme. A new Settings › Appearance › Theme ListPreference (System/Light/Dark, default System) is stored only in BlackBoxLoader and applies without a restart. Only the app module changes; there are no new dependencies and no new automated tests (manual QA).

Key Decisions

  • One DayNight Theme.BlackBox with md_theme_* colors (day in values/, night in values-night/). The manifest is unchanged.
  • Init in App.onCreate, gated by isMainProcess(). The DynamicColors precondition uses the class prefix top.niunaijun.blackboxa.. The trailing dot keeps Bcore's top.niunaijun.blackbox.app.LauncherActivity out.
  • Single source of truth: a String delegate in BlackBoxLoader. The ListPreference is persistent=false, and its dedicated listener shows no restart toast.
  • @color/primary is kept only as the CatLoadingView background: primary in day, primaryContainer in night, so the white label keeps 4.5:1.
  • Status bar = colorSurface with light icons on API 23+ through a values-v23 override (Base.Theme.BlackBox). API 21–22 keeps the M3 default. The navigation bar stays at the system default.
  • WelcomeTheme extends Theme.BlackBox and overrides only windowBackground.
  • material-dialogs is themed via md_* attributes; its 12 call sites are untouched.
  • ToolBarColorStyle → ThemeOverlay.BlackBox.Toolbar. Colors accent, primary_dark and primary_light are removed. primary_text and secondary_text stay because the dead item_xp.xml uses them.
  • snake_case color names (md_theme_on_primary_container) per the standard, not the Theme Builder camelCase.

Goal

Deliver a Material 3 look with a real color scheme and full dark mode across all host screens. Users can follow the system theme or force Light or Dark from Settings without restarting, and Bcore and guest apps stay untouched.

Scope

  • Theme re-parent, M3 role set, values-night, values-v23 status bar
  • Dynamic color (API 31+, main process, host activities)
  • Surface toolbar + ThemeOverlay.BlackBox.Toolbar
  • Tokens in touched layouts: item_app/fake/package/gms, activity_main, activity_list, view_toolbar
  • ic_add / ic_search tints, splash, drawable-night/ic_empty.xml
  • AppsAdapter placeholders, MaterialSwitch (GMS), robust subtitle click
  • material-dialogs md_* attributes

  • RELEASE_NOTES, roadmap and project docs updates

Out of scope

  • MaterialAlertDialogBuilder migration; replacing SimpleSearchView/CornerLabelView/RVAdapter
  • preference-ktx upgrade, core-splashscreen
  • osmdroid tile inversion, dynamic-color toggle

User Stories

As an end user who uses dark mode at night, I want the sandbox UI to follow the system dark theme automatically, so that it does not blind me or flash white on launch.
As an end user, I want to force Light or Dark from Settings › Appearance › Theme, so that the app looks the way I prefer. The change applies immediately and persists.
As an end user on Android 12+, I want the app to pick up my wallpaper colors (Material You), so that it matches my device.
As a user of existing features, I want install, launch, the long-press menu, GMS, fake location and the settings switches to behave exactly as before.

Technical Approach

Theme resolution

Manifest → Theme.BlackBox. In values/themes.xml, Base.Theme.BlackBox holds the roles, type/shape tokens, md_* attributes and actionMenuTextColor; Theme.BlackBox extends it. values-v23 adds statusBarColor=?attr/colorSurface and windowLightStatusBar=?attr/isLightTheme. Night selection comes through the values-night/colors.xml qualifier. Style prefixes never collide with Bcore BTheme / LauncherTheme.

Startup (main process only)

App.onCreate, after super.onCreate(): if isMainProcess(), call setDefaultNightMode(mapped loader value), then DynamicColors.applyToActivitiesIfAvailable with the class-prefix precondition. :pN and server processes skip both. Bcore LauncherActivity fails the precondition. This is the allowed lifecycle-hook exception for direct BlackBoxCore access.

Setting change

Listener: loader setter → setDefaultNightMode. Host activities recreate, and SettingFragment re-reads its value from the loader. The default SharedPreferences file is never written for theme_mode.

Color flow and data

Layouts and drawables → ?attr/ roles → theme → md_theme_* or the dynamic overlay. Only three spots are bound to @color/ (the LoadingActivity alias, the splash via colorBackground, and third-party fallbacks); they follow night mode but not dynamic color. Data: one new key in the delegate file; clearing app data resets it to system. There are no Bcore changes.
